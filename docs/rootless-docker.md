# Rootless Docker

Omarchy runs ordinary development containers in a per-user rootless Docker daemon while retaining a separate rootful Docker daemon for the Windows VM. This keeps the Docker CLI, Compose, Buildx, and image format unchanged while removing the root-equivalent `docker` group from the development path.

## Runtime boundary

The user daemon is `docker.service` from `docker-rootless-extras`. It listens on `$XDG_RUNTIME_DIR/docker.sock`, stores engine data below `~/.local/share/docker`, and reads daemon configuration from `~/.config/docker/daemon.json`. `default/systemd/user-environment-generators/60-omarchy-rootless-docker` and `default/bash/env-bootstrap` export `DOCKER_HOST` only after `~/.local/state/omarchy/rootless-docker/enabled` exists.

The system daemon remains socket-activated for `omarchy-windows-vm`. Its vendor drop-in makes `/run/docker.sock` root-owned with mode `0600`, and migration verifies both the effective systemd socket properties and the daemon process's open sockets before and after connection revocation. A later administrator override, custom Unix listener, or TCP listener stops automatic migration. The Windows command always selects the protected socket explicitly after authenticating with `sudo` or `pkexec`; user Docker settings and `DOCKER_HOST` cannot redirect the privileged VM command.

## Fresh installs and additional users

The root setup allocates each account a nonoverlapping subordinate UID and GID range of at least 65,536 IDs and writes `/var/lib/omarchy/rootless-docker/enabled`. User finalization creates the private marker and daemon config, then first-run setup enables the rootless service only for that initialized account. Existing accounts follow the same order during migration; no global user-unit symlink can start Docker for another account before its subordinate IDs and daemon config exist.

The migration's machine-wide enabled marker is written only after the shared rootful inventory has migrated and `/run/docker.sock` has been restricted. When another account later runs the per-user migration, it initializes that account's rootless daemon and returns before inspecting the retained rootful recovery store.

## Existing-install migration

`migrations/1789164756.sh` installs the rootless runtime, allocates subordinate IDs, restarts and proves the rootless daemon with that account's configuration, secures any current account's Windows definition, restricts the old API socket to root, and preflights every rootful container. An existing Windows container is reconciled from the hardened Compose definition while a root-only, synchronized lifecycle record preserves whether it was running or stopped across interruption; the new runtime must use web protection and the current account's protected mount anchors. Only after those checks does the migration durably claim the machine-wide source inventory for that account. A container named `omarchy-windows` is exempt only when its image, Compose identity, devices, capabilities, ports, environment, and UID-bound mounts match Omarchy's managed VM. A blocker in any source prevents the batch from stopping its first container or assigning the migration owner. Compose, credentials, legacy-definition removal, owner selection, and machine completion are synchronized to disk before migration continues.

The automatic path accepts running or never-started containers with stock bridge networking, localhost-only unprivileged published ports, private local named volumes, supported resource limits, root users with Docker's default capability ceiling or stricter settings, numeric non-root image users that already drop every capability, and the stock runtime and namespace boundaries. It rejects already-exited containers whose historical exit state cannot be recreated without rerunning them, privileged containers, added capabilities, devices, host or shared mounts, named image users whose effective UID is ambiguous, numeric non-root image users whose capability ceiling cannot be reproduced exactly, custom networks, namespace sharing, custom runtimes, altered confinement, custom logging, reserved migration labels, and unknown nondefault host settings.

For each accepted container, the migrator stops the source cleanly and durably seals its source-volume fingerprints before rootful Docker is restarted to revoke existing clients. Every seal is checked again before the first destination transfer. The migrator commits the writable layer, transfers that image through Docker's native save/load format, and creates an unpredictable inert guard that pins every owned volume while contents and metadata are copied inside the RootlessKit user and mount namespace. The application container does not exist during that long copy. Copied volume filesystems are synchronized before completion metadata is published. After transfer, a stopped `runc` application container joins the guard on the verified volumes; the guard is removed only after Docker proves both references, and the application container must still be never-started before finalization. A unique volume event marker proves the daemon retained the complete transfer window; a transient mount by any other container or missing event history stops automatic finalization. The migrator verifies environment, application config, runtime, limits, capabilities, mounts, ports, restart policy, logging, volume fingerprints, and lifecycle before writing a receipt bound to full source and destination snapshots. If one transfer fails, every later source that the batch already quiesced is restored in reverse order.

Before the destination is first started, an error removes only the exact journal-owned destination container and restores the source. The first journal directory entry, each journal update, and each rename are synchronized before they can authorize mutation. Journal-owned volumes remain available for ownership verification; a retry attaches each verified volume to the stopped destination before emptying and copying the current stopped source again, so a concurrent name replacement, partial transfer, or later source deletion cannot damage unrelated data or leave stale entries. Resume requires Docker to prove that the destination has never started and to replay the persisted event window before starting it. Once a destination start has been attempted, automatic retry and source restoration stop for manual recovery because either side may contain new writes. A durable completion receipt takes precedence over a leftover journal if power fails between those two writes. Successful sources remain stopped with their restart policy disabled; they are retained in the rootful engine as recovery copies.
