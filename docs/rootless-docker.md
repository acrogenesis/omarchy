# Rootless Docker

Omarchy runs ordinary development containers in a per-user rootless Docker daemon while retaining a separate rootful Docker daemon for the Windows VM. This keeps the Docker CLI, Compose, Buildx, and image format unchanged while removing the root-equivalent `docker` group from the development path.

## Runtime boundary

The user daemon is `docker.service` from `docker-rootless-extras`. It listens on `$XDG_RUNTIME_DIR/docker.sock`, stores engine data below `~/.local/share/docker`, and reads daemon configuration from `~/.config/docker/daemon.json`. `default/systemd/user-environment-generators/60-omarchy-rootless-docker` and `default/bash/env-bootstrap` export `DOCKER_HOST` only after `~/.local/state/omarchy/rootless-docker/enabled` exists.

The system daemon remains socket-activated for `omarchy-windows-vm`. Its vendor drop-in makes `/run/docker.sock` root-owned with mode `0600`, and migration verifies from the daemon process's open sockets that this is its only API listener. Custom Unix or TCP listeners stop automatic migration. The Windows command always selects the protected socket explicitly after authenticating with `sudo` or `pkexec`; user Docker settings and `DOCKER_HOST` cannot redirect the privileged VM command.

## Fresh installs and additional users

The root setup allocates each account a nonoverlapping subordinate UID and GID range of at least 65,536 IDs, enables the rootless service globally, and writes `/var/lib/omarchy/rootless-docker/enabled`. User finalization then creates the private marker and daemon config before first login starts the service.

The migration's machine-wide enabled marker is written only after the shared rootful inventory has migrated and `/run/docker.sock` has been restricted. When another account later runs the per-user migration, it initializes that account's rootless daemon and returns before inspecting the retained rootful recovery store.

## Existing-install migration

`migrations/1789164756.sh` installs the rootless runtime, allocates subordinate IDs, starts and proves the rootless daemon, secures any current account's Windows definition, restricts the old API socket to root, and preflights every rootful container. Only after those checks does it claim the machine-wide source inventory for that account. A container named `omarchy-windows` is exempt only when its image, Compose identity, devices, capabilities, ports, and UID-bound mounts match Omarchy's managed VM. A blocker in any source prevents the batch from stopping its first container or assigning the migration owner.

The automatic path accepts running or never-started containers with stock bridge networking, localhost-only unprivileged published ports, private local named volumes, supported resource limits, root users with Docker's default capability ceiling or stricter settings, numeric non-root image users that already drop every capability, and the stock runtime and namespace boundaries. It rejects already-exited containers whose historical exit state cannot be recreated without rerunning them, privileged containers, added capabilities, devices, host or shared mounts, named image users whose effective UID is ambiguous, numeric non-root image users whose capability ceiling cannot be reproduced exactly, custom networks, namespace sharing, custom runtimes, altered confinement, custom logging, reserved migration labels, and unknown nondefault host settings.

For each accepted container, the migrator stops the source cleanly, commits its writable layer, transfers that image through Docker's native save/load format, creates a stopped `runc` destination to pin every owned volume, and copies volume contents and metadata inside the RootlessKit user and mount namespace. It verifies environment, application config, runtime, limits, capabilities, mounts, ports, restart policy, logging, volume fingerprints, and lifecycle before writing a receipt bound to full source and destination snapshots. If one transfer fails, every later source that the batch already quiesced is restored in reverse order.

Before the destination is first started, an error removes only the exact journal-owned destination container and restores the source. Journal-owned volumes remain available for ownership verification; a retry attaches each verified volume to the stopped destination before emptying and copying the current stopped source again, so a concurrent name replacement, partial transfer, or later source deletion cannot damage unrelated data or leave stale entries. Resume requires Docker to prove that the destination has never started. Once a destination start has been attempted, automatic retry and source restoration stop for manual recovery because either side may contain new writes. A durable completion receipt takes precedence over a leftover journal if power fails between those two writes. Successful sources remain stopped with their restart policy disabled; they are retained in the rootful engine as recovery copies.
